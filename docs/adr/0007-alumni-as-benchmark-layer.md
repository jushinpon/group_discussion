# ADR-0007：校友（alumni）作為獨立的知識層與基準線

- 狀態：已接受
- 日期：2026-11-01
- 決策者：Pon

## 背景

現有系統只追蹤在學學生（`students/`），判定他們相對 `goals.md` 的進度。這留下兩個缺口：

1. **機構記憶流失**：畢業生的 meeting 投影片、paper review、自有數據與學位論文散落在信箱裡，沒有任何結構化入口。新學生問「這個子題以前有人做過嗎」時，只能重讀 5,000 封信。
2. **沒有基準線**：`goals.md` 的「應該做到什麼」目前由 agent 從信件推論。但同一題目上，**已經畢業的人做到了什麼**是可觀測的答案——論文、期刊、答辯內容都是證據。缺了這一層，進度判定只能說「有沒有動」，不能說「離完成還差多少」。

## 決策

### 1. 校友放 `alumni/`，與 `students/` 完全分離

校友**不套用**進度判定語意（不會是 on-track／at-risk／off-track），也不進週報。他們是參考層，不是被評價的對象。

`students.yaml` 的 `parked:` 條目若確認已畢業，改列 `alumni.yaml`，不留在學生名冊（避免「畢業生被算成沒交作業的學生」）。

### 2. 每位校友有 `benchmark` 頁，回答「這個子題做完了長什麼樣」

`alumni/<slug>/wiki/benchmark.md` 要能回答：

- 他的**最終產出**是什麼（學位論文題目、期刊論文、達到的效能／性質／方法）
- 做到那個程度需要哪些**階段**（文獻 → 勢能／模型 → 收斂驗證 → 系統性計算 → 分析與寫作）
- 每個階段留在信箱裡的**可觀測痕跡**（哪一份投影片、哪一份數據）

因此 benchmark 不是傳記，而是**可比對的階段清單**。

### 3. 相似子題檢索是主要用途

`scripts/topic_match.py` 對「現任學生的 goals／近期週報」與「校友的主題與 benchmark」做比對，輸出：

- 最接近的 3 位校友與其子題
- 校友在那個子題上**已經走完的路徑**（可作為給學生的 indication）
- 校友留下的可讀材料（投影片、論文、數據）

給學生的建議必須附來源（哪位校友、哪一封信、哪一份附件），不得由 agent 自行想像研究方向。

### 4. 學位論文是校友層的核心，且不在信箱裡

校友的學位論文在**學校論文系統**（NSYSU eThesys／國家圖書館 NDLTD），不在 group meeting 信件中。校友層必須納入論文層（題目、摘要、全文狀態），這是唯一能提供「完成態」樣貌的來源。

論文 PDF 受授權限制（多數設定校內外開放年限），**只在使用者自己的連線環境下抓取**，且不進 git。

### 5. 附件政策：投影片與自有數據優先，已發表 PDF 只留檔名

校友郵件總量 4,007 封、22.4 GB。已發表的 paper PDF 可用檔名（含標題）事後由 DOI 取回；**投影片、Excel、程式碼、圖片**才是不可回復的材料。

因此 `scripts/ingest_alumni.py` 預設 `--pdf-mode index`（大於 3 MB 的 PDF 只索引檔名），需要時可 `--pdf-mode full` 指定單一校友補齊。

## 後果

- 校友 wiki 由 agent 建立，但 `benchmark.md` 與「建議給學生什麼」必須經 Pon 確認才寫入（同 goals 的人工確認原則）。
- 校友資料同樣不進 git（`alumni/*/attachments/`、`alumni/*/mail/` 皆排除），只有 wiki、`alumni.yaml`、論文索引進版控。
- 週報（cron）只能**引用**校友層，不能改寫校友 wiki。
- 新增 `alumni.yaml` 作為名冊唯一來源；slug 為身分鍵，同一人的多個 email 合併同一 slug。
